# 交互设计方案（语言为主 · 交互为辅）

> 适用：FamilySoul 世界引擎 / 双真人客户端（王甯、紫嫣等）
> 目标：不破坏"说话就是世界"的手感，同时让**花钱、去某地、带人走、两人协作**这类有参数的动作可靠、可测、不误解。

---

## 0. 一句话原则

**语言负责"说什么、怎么想"，交互只负责"确认、消歧、授权"三件脏活。**

比例参考：**语言 95%，交互 5%**；一次会话点击 0–2 下。

---

## 1. 哪些交给语言，哪些交给交互

| 必须交给语言 | 可以交给交互 |
|---|---|
| 对话、情绪、调情、试探、谈判 | 要花钱的确认（房钱、赏银、赎身） |
| 承诺、威胁、劝和、挑唆 | 地名有歧义或世上还没有此地 |
| 描述意图（"我想带她走"） | 带谁走 / 要不要跟（同行授权） |
| 对结果的接受或拒绝 | 双真人之间的邀约（知情 + 接受） |
| 任何"结局"的判断 | 参数选择（房型、兵力、数额） |

**铁律：交互只提交"意图"，绝不保证"结果"。**

```
点"求她原谅" ≠ 她一定原谅
点"纳她为妾" ≠ 她一定答应
```

## 2. 交互的形态：浮条，不是弹窗

### 2.1 基本规则

```
位置：输入框正上方一行
数量：同屏永远只有 1 条（新顶旧）
消失：不自动消失
```

**它只被三件事结束：**

```
① 被消费（你点了 / 你说了等效的话）
② 被替代（出现新的待办）
③ 被划掉（你点了 ×，或说了"算了/不去"）
```

### 2.2 超时不消失，只降级

```
30 秒未处理 → 颜色降一档（还在）
2 分钟未处理 → 收进"待办"，聊天区留一行小字
永不出现倒计时，永不"错过就没了"
```

### 2.3 什么时候自动清除

**只有一种**：你说了完全无关的话（"算了，不说这个""走，回家"）。

**因为你的注意力已经走了。**

### 2.4 打字必须等效

```
浮条 [ 付 3 两 ]
你说"付了" / "行" / "就上房吧"
→ 完全等效
```

**不点也能玩下去**，这是浮条存在的底线。

---

## 3. 三种该浮出的场景

### 3.1 确认（要花钱）

```
（孙掌柜把钥匙往柜台上一推）"上房，三兩。"
  [ 付 3 两 ]   [ 换通铺 2 钱 ]   [ × ]
```

### 3.2 消歧（地名不明 / 世上还没有）

```
你说"去小茶摊"
  [ 让天道造一处「小茶摊」 ]   [ 就近找个茶摊 ]   [ × ]
```

**绝不静默失败，也绝不擅自改名成别的铺子。**

### 3.3 授权（带人走 / 双真人邀约）

见第 4、5 节。

## 4. 同行（party）模型

### 4.1 状态

```
world.party = { husband: ['liuwenxia'] }
```

**显式名单，持久化，不靠每句话去猜。**

### 4.2 加入与解除

```
"带上紫嫣""紫嫣跟我去""一起去"   → 加入
"你留下""别跟了""各走各的"       → 移出
```

### 4.3 移动时的判定顺序

```
① 同行者是否与发起人同处一地？
   否 → 不动她（可记"她随后赶来"）
② 她是否愿意？（怨气、手头活计、名分顾虑）
   否 → 她不走，回一句理由（理由来自账本）
③ 同意 → 与发起人同时移动
```

### 4.4 拒绝必须有理有据

```
怨气 ≥ 40          → 冷面推辞
手头有差事（新鲜）  → "走不开"
名分不便           → 正妻去客栈有失体面
```

**activity 必须带时间戳，超过 2 个世界小时不算"手上有事"。**

### 4.5 双向对称

```
她说"跟我去医馆" → 他跟着走；她移动时也要同步他
他单独回家       → 她不被带走
```

**两条都要过回归，缺一条就会反向复发。**

## 5. 双真人协议（开房为范例）

### 5.1 谁发起、谁付钱、谁确认

```
发起人 = 先开口"开房"的那个人
只有发起人端浮出确认（因为钱从共同银两出，记 paidBy）
```

### 5.2 另一端只知情，不打断

```
输入框上方一行小字：
  「王甯已开好上房（3两），等你上去。」
   [ 上去 ]  [ 先不 ]
```

**不弹窗、不阻塞、不强制。**

### 5.3 状态机（写在 world 里，不在客户端）

```
offered → paid → entered
        ↘ expired（房钱不退，房空着）
```

字段建议：

```js
pendingRoom = {
  id, inn, roomName, price, paidBy,
  invitee: 'liuwenxia', status: 'offered' | 'paid' | 'entered' | 'expired',
  day, hour, ttlHours: 6
}
```

### 5.4 冲突与幂等

```
两人同时开房 → 账本只认第一条 pending，另一端提示"房已开好"
重复提交同 actionId → 只扣一次钱
钱不够 → 发起人端提示可换房型，不扣钱
```

### 5.5 私密场景的硬门禁

```
两人都在房间 → 可解锁
只有一个在   → 天道拒绝并说明
```

## 6. 多真人协作（以攻城为范例）

### 6.1 指挥权

```
一场战役只有一个 commander（主将），其余为 ally（副将）
盟友不能改命令，但可以：贡献兵粮、提建议（语言）、单方面带自己的兵退出
```

### 6.2 战役对象

```js
battle = {
  id, city, commander,
  allies: [{ id, troops, supplies }],
  status: 'gathering' | 'marching' | 'sieging' | 'won' | 'lost' | 'retreat',
  round, startedDay, log: []
}
```

### 6.3 回合制结算

```
每个世界小时推一回合，由时钟驱动
不是"谁说话谁结算"，避免同回合双结算
```

### 6.4 分账

```
战利品按出兵比例分
损失按各人部队算
断线 → 自动转"围城"，不自动开战
```

### 6.5 禁令

```
不许两个 commander
不许盟友静默改战局
不许"必然胜利"的主角光环
```

## 7. 语言解析失败时的行为

```
① 不猜人名、不造替身、不擅自改名
② 明确告诉用户"没听懂/世上没有"
③ 给出 1–2 个替代，可点可忽略
④ 永不静默失败
```

**例**：`"去拾啥"` —— 不是地名 → 不造人、不造景，只问一句。

---

## 8. 绝不做成交互的东西

```
❌ 情绪选择（"选择你的回话"）
❌ 常驻九宫格菜单
❌ 每句话下面挂按钮
❌ 点完直接跳文本、没有画面
❌ 叙事倒计时（"掌柜等急了"）
```

**把"说什么"变成选项，就从世界退化成 galgame。**

---

## 9. 验收指标

| 指标 | 目标 |
|---|---|
| 每轮点击次数 | ≤ 2 |
| 阻塞式弹窗 | 0 |
| 浮条自动消失 | 0 |
| 动作确认到画面 | < 1.5 秒 |
| 双真人状态不一致 | 0（同一 version） |
| 同 actionId 重复结算 | 0 |
| 语言解析失败静默 | 0 |

---

## 10. 与七层管道的关系

```
Intent  ← 语言或点击，同一种对象
Gate    ← 在场/身份/资源/地名存在性（纯函数）
Reserve ← 浮条 = 一次"待确认占用"，带 TTL
Arbiter ← 天道判"成不成、怎么演"
Apply   ← 唯一写者，按 actionId 幂等
Narrate ← 只读事实，写画面与台词
```

**浮条本质是 Reserve 层的可视化**——不是 UI 装饰。
