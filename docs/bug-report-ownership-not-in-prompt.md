# Bug 报告（修订）：产业归属是客观事实，不该因"谁问"而变

> 涉及账号：**紫嫣号（真人成员 liuwenxia）**，不是新注册号
> 严重级别：**高**（世界既定事实被 NPC 当面否认）
> 结论：**归属事实必须全局唯一、与提问者无关；现在是按视角各拼一套，所以才会出现"谁问谁编"**

---

## 一、现象

紫嫣号在「运河码头三层大酒楼」问自家掌柜周有福："这是谁家的产业？"

```
第一次：这楼是徽州盐商汪家的产业……
第二次：这楼是知府衙门里赵主簿家三房的产业……
```

**两次都不一样，而且都不是真的。**

**真实事实只有一条：**

```
运河码头三层大酒楼 → 东家 王甯（owner=husband）
在岗：周有福（掌柜）、陈二（伙计）、何顺（厨子）
```

---

## 二、核心错误（我之前的修法方向就错了）

**错误认知**：把"这店是谁的"当成"她的身份卡里的一条"。

**正确认知**：

```
产业归属 = 世界的客观事实
它不因提问者是紫嫣、是相公、是路人、是掌柜本人而改变
```

**所以不能"给她加一条"，而必须"让世界在任何场景下都带着这条"。**

现在的实现里，这条事实是**按会话临时拼的**：

| 场景 | 有没有这条事实 | 结果 |
|---|---|---|
| 相公号在自己产业里 | 部分有（`【用人】`注入时） | 有时答对 |
| 紫嫣号在自己产业里 | 没有 | 现编"汪家" |
| 周有福被代演 | 没有（只给了"你是掌柜"） | 现编"赵主簿家" |
| 路人在同一处发问 | 没有 | 又一个版本 |

**同一件事，四个回答。这就是"扯淡"的来源。**

---

## 三、正确模型：一条事实源，全场景生效

```
事实源：property（owner + staffIds + placeId）
产出：placeFacts(地点) → 一段固定文本
       「此处产业：运河码头三层大酒楼，东家：王甯。
         在岗：周有福（掌柜）、陈二（伙计）、何顺（厨子）。」
```

**这段文本必须被三处同时使用，且内容完全一致：**

```
A. 任何真人账号的对话（不管是谁，只要场景在这个地点）
B. 任何 NPC 的代演（尤其是自家雇工）
C. 她的身份卡（可以有，但不是唯一来源）
```

**判定标准（写进代码审查）**：
**同一时刻、同一地点，不同账号问同一个人"这是谁家的"，回答必须一致。**

---

## 四、为什么现在的改法（未提交的 `member-card.js`）没解决

它做的是"**给她那一侧**加一条地方归属"，于是：

```
· 相公号 → 另一条路径（可能没有）
· 周有福被代演 → 还是没有东家
· 新账号 → 更没有
```

**事实仍然散落各处，只是给紫嫣补了一块。**

另外它还有三个具体问题：

```
① 名字包含匹配：产业"运河码头三层大酒楼".includes("运河码头") === true
   → 站在码头也声称自己在酒楼里
② 把人名写死：周有福、陈二、何顺 硬编码，人走/改名/换人后即成假话
③ 规定台词："必须斩钉截铁回答这是王甯的" → 替天道下台词
```

---

## 五、建议修法（一处产出，三处引用）

```
新增：placeFacts(world, placeId)  —— 唯一产出点
      输入地点 id，输出固定的一句话事实（含东家真名、实际在岗者）
      数据来源：property.placeId / owner / staffIds；人名一律查 actors 现名

引用：
  1) 每轮对话的"场景事实"里（不分账号，谁在这就在这）
  2) NPC 代演时的"你是谁"里（在岗者额外带上"东家是谁"）
  3) 她的身份卡（可选，内容同上）
```

**禁止**：任何地方再手写人名、手写金额、手写"必须这样回答"。

---

## 六、验收标准（按"与谁问无关"来验）

```
□ 紫嫣号问周有福"这是谁家产业" → 王甯的
□ 相公号问同一个周有福 → 同样的答案（一字不差）
□ 换一个路过的 NPC 问 → 同样的答案
□ 站在运河码头（不是酒楼）→ 不会声称自己在酒楼里
□ 把周有福调离酒楼后再问 → 不再说他在岗
□ 把周有福改名为"周掌柜" → 所有地方自动跟着变，不改代码
□ 紫嫣站在自己的于家酒肆 → 答"紫嫣自己的"，不是王甯的
```

## 八、附：现有的几处改动为什么属于"补丁"（证据）

> 下面四条都是**当前仓库里已存在**的代码（三条已提交、一条在工作区）。
> 目的不是否定动机（动机都对：让掌柜认东家、让酒楼归属明确），
> 而是说明**这样写会在别处继续出问题**。

### 证据 1：heal.js「确权」把所有无主产业判给王甯

```js
// src/world/heal.js ⑬
for (const p of world.assets.properties) {
  if (!p.owner || p.owner === 'husband' || p.owner === 'wangjia') {
    p.owner = 'husband';
  }
}
```

**问题**：
- 这是**按个案改数据**，不是修规则；
- 更危险：**任何"暂时没写 owner"的产业都会被吞成王甯的**——新玩家开的店、NPC 刚盘下的铺子、天道新建的产业，全都会变成"相公的"；
- 修 bug 的代码本身会造 bug。

**正确做法**：`owner` 在**创建那一刻**就写死（谁掏的钱就是谁的）；无主数据只能清一次，且要在"创建路径"上补默认值，不能留常驻的强制赋值。

---

### 证据 2：提示词里写死人名与"绝对严禁"

```js
lines.push('【相公身份与尊称铁律】相公王甯是这间三层临街大酒楼的【全资大东家/幕后大老板】！
  沈婉儿亲自主理筹备开张；何顺/吴有德等为相公招募聘用的大掌柜！…');
```

**问题**：
- **写死两个人名**：何顺、吴有德是临时补位建的角色，改名/辞工/换人后，这句话就变成假话；
- **只对"这间酒楼"生效**：换个地点（茶坊、货栈、别人家铺子）照样乱认东家；
- 同一件事在四处各写一段（heal、提示词、member-card、代演），**四处会互相打架**。

**正确做法**：只写一条规则产出事实（`placeFacts`），谁用谁读，不许各写一段。

---

### 证据 3：`member-card.js` 的 `placeLine`（工作区未提交）

```js
pn.includes(loc.name) || loc.name?.includes(pn)     // 名字包含匹配
"在场所有人（周有福、陈二、何顺等）全是王相公雇来的" // 写死人名
"凡被问及东家，必须斩钉截铁回答：这是王甯王相公的产业！" // 规定台词
if (locId === 'canal_restaurant' || 名称含"酒楼")       // 第二套判定
```

**四个问题**：误判地点、写死人名、替天道下台词、双份判定。
**而且它只覆盖"她那一侧"**，相公号、NPC 代演、新账号仍然没有这条事实。

---

### 证据 4：把"接话分身"写死成剧情分支

```js
haremNotice = `（【当前接话分身：货栈大娘子·杨采云】：…若提及管事，便命管事当面回话并查底册！）`
haremNotice = '（【相公当面质问随科】：…必须由【随科】首先开口答复，如实交代底册文书…）'
```

**问题**：这是在**替天道演剧情**——谁先开口、说什么、带什么态度，全被代码规定了。
**违反第一铁律**：引擎只提供事实与阻力，不得规定怎么演。

---

### 这四条的共同病根

```
把"世界的事实"当成了"这个场景该说的台词"
  ── 事实：这处产业东家是王甯，在岗三人（一条，全局唯一）
  ── 台词：必须斩钉截铁回答"这是王甯王相公的产业"（不许写）
```

### 正确的三句话

```
① 产业归属：创建那一刻就定；读取时只读 property.owner → 查 actors 现名
② 任何场景（谁的号、谁被代演）都注入同一条 placeFacts(地点)，一字不差
③ 不给"必须怎么说"，只给"事实是什么"
```

**审查时可以一句话判**：
**同一地点、同一时刻，换任何人问同一个人"这是谁家的"，答案必须一样；若答案不同，就是事实没做成全局。**

## 九、同类缺口：婚配与住处，也是"账上没有、他就随口编"

> 同一类病：**世界里没有这条事实 → 天道只能编 → 你无法证实**。

### 现象（新角色 陆羽，实测）

```
人物志：陆羽 · 求学的生员 · 男 26 岁 · 在临江客栈 · 身上 20 两
        关系：—     家底：无家底     产业：—

聊天：
你：你娶妻了吗？
陆羽：自然娶了，我屋里那位就是。
你：那你们为啥在客栈？没有房产吗？
陆羽：房产倒是有一处，在城南巷子里，就是离书肆远了些。
```

**三句话，三处无法证实：**

| 他说的话 | 账上有没有 | 结论 |
|---|---|---|
| "我娶了" | 没有 spouse 字段 | 编的 |
| "我屋里那位就是" | 场景里没有这个人 | 编的 |
| "城南巷子有一处房" | home 只有客栈（且与他人共用） | 编的 |

### 根因

```
1. 角色没有"婚配状态"字段（只有个别内置角色写了 spouse）
2. 角色没有"住处性质"字段（自有 / 租住 / 寄居 / 客栈）
3. 看板与人物志都不显示这两项 → 你连核对的地方都没有
```

**所以不是他编得像，是我们根本没把"有没有老婆、有没有房"当成事实存起来。**

### 必须补的两条事实

```jsonc
// 婚配
"marital": "single" | "married" | "widowed" | "concubine",
"spouse": "<actorId>" | null

// 住处
"residence": { "type": "own" | "rent" | "inn" | "family", "placeId": "house_xxx" }
```

**派生规则（读时算，不手填）**：
```
有 spouse 且双方都活着 → 已婚
residence.type = inn    → "住客栈"
residence.type = own    → "自有民宅"
household 且无名分      → 家仆 / 寄居
```

### 显示要求（客户端 + 看板都要有）

```
人物志：
  婚姻：未婚 / 已婚 · 配偶「某某」 / 寡居
  住处：自有民宅（城南小院） / 租住客栈（临江客栈） / 寄居王府

看板人物表：加两列（婚姻、住处），或追加在"身份"列后
```

### 相关规则（顺带定清楚）

```
① 新角色：marital=single、spouse=null、residence=inn
② 婚礼/纳妾走世界流程（天道裁定 + 花钱 + 事件流），成功后写 spouse
③ 有了 spouse，他说"我娶了"才是真的；说"没娶"就是假的
④ 未经流程自称有配偶 → 应当自相矛盾，而不是随口编出整套家室
```

### 验收

```
□ 新角色人物志显示：婚姻 未婚 · 住处 客栈
□ 问"你娶妻了吗" → 答没有（或含糊，但不许编出配偶）
□ 走完一场婚事 → 显示 已婚·配偶某某，问他就答有
□ 配偶改名 → 人物志跟着变（按 id 取名，不存名字）
```
