# 世界「活起来」的路线（底座 × 天道）

> 铁律不变：AI 是天道，不写剧本、不给结局。  
> 这份文档只回答一件事：**怎么让世界在玩家不看着的时候也自己转，而且转得对得上账。**

---

## 一、先把「活」定义清楚（不然会做成动画）

一个世界算「活」，要同时满足六条。少一条就是「半活」：

| # | 不变量 | 现在的状态 | 验收方式 |
|---|---|---|---|
| 1 | **每个人都有自己的事**（目标 + 日程 + 去处） | 有位置与作息，缺「目的」 | 随便点 10 个 NPC，都能说出他今天要办什么 |
| 2 | **玩家不在场，世界照转** | 时钟在走，但多数变化是「日志」 | 关闭客户端 6 小时，回来看账与人事都变了且自洽 |
| 3 | **事件有因果链** | 事件多为独立记录 | 任一事件能追到「谁起的头 → 谁受影响 → 后来越怎样」 |
| 4 | **经济闭环** | 收支能算，但反馈慢 | 一笔买卖 → 粮价/库存/伙计工钱/东家银两四处同时变 |
| 5 | **关系会自己变** | 关系主要靠玩家互动改 | 不见面的两个人，交情也会因事而冷热 |
| 6 | **天道只解释、不发明事实** | 已靠事实注入 + 出口校验约束 | 任取 20 轮对话，事实错误 ≤ 1 处 |

**「半活」的根因不是模型不行，是第 1、2、3 条没有底座支撑。**  
模型只能解释它看到的事实；底座不生成「事」，天道就只能编。

## 二、架构方向：三层各管一件事

```
┌─────────────────────────────────────────────┐
│  叙事层（天道 / LLM）                        │
│  只做：把事实讲成人话、决定某人此刻怎么应    │
│  不许：凭空造人、造物、造钱、造地点          │
├─────────────────────────────────────────────┤
│  规则层（底座 Simulation）                   │
│  做：目标推进、日程、交易、人情、案子、灾荒   │
│  产出：事实（facts）+ 事件（event）+ 变更     │
├─────────────────────────────────────────────┤
│  状态层（world state，单一写入口）            │
│  做：谁在哪、有多少、归谁、什么关系           │
│  约束：moveActor / money / 账本 唯一写者      │
└─────────────────────────────────────────────┘
```

**关键判断**：世界「活」不是靠模型多说几句，而是靠**规则层每小时/每天推进一次**，模型只负责在需要时把发生的事讲出来。

## 三、要做的四件事（按优先级）

### P0 · 离线推进（最要紧）

```
现状：时钟在走，但"事"不推进；玩家不来，世界基本静止
要做：每个时辰跑一次 "World Tick"
  · 每座城的粮价/治安/商路 各自演化
  · 每户人家：中馈、雇工、债、病、婚丧 各推进一格
  · 每个有目标的人：朝自己的目标走一步（不必然成功）
产出：只写事实与事件，不写台词
验收：关客户端 6 小时，回来账能对上，人事有变化
```

### P1 · 给 NPC「目的」

```
现状：NPC 有 role、有位置，但没有"今天要办什么"
要做：目标生成器（按身份/处境推）
  · 家丁：护院、听差、看门（现在已有门房差事）
  · 掌柜：进货、催账、应酬
  · 官差：办案、收税、押送
  · 游侠：找活、寻仇、投靠
验收：任点 10 人，说得出去处与目的；且目的会随时间变
```

### P2 · 事件因果

```
现状：事件是流水
要做：事件带 parentId，一桩事能生出后续（欠债 → 催账 → 官司）
验收：抽一条事件能往上追三代、往下看后果
```

### P3 · 观测面板（不然你看不见它活）

```
现状：后台只有数字
要做：一张"世界日报"——今日何处生了什么事、谁跟谁起了争执、哪家亏了
验收：每天打开能看懂世界发生了什么（不靠聊天）
```

## 四、天道和底座怎么配合（分工写死）

```
底座负责：事实、边界、结算、时间
天道负责：解释、措辞、临场反应、把事实讲圆

底座给天道的"事实包"必须是：
  ① 这间屋子有什么（陈设）
  ② 这里的人是谁、什么身份（称谓）
  ③ 钱、粮、兵、债的准数（行情）
  ④ 刚刚发生了什么（事件）
  ⑤ 谁能说话（在场铁律）

天道回写的只允许两类：
  · [[world:...]] 标签（由引擎结算，不让它自己改账）
  · 台词（由引擎校验在场与身份）
```

**契合度不是靠调模型参数，是靠「事实包」够不够准、够不够全。**

## 五、关于「三维立体」

你问的应该是：**以后聊天界面里直接显示 3D 真实场景**。

**技术上可以，但要分清两件事：**

```
① 世界模型的三维性：地点有层级、有方位、有时辰——这个底座已经有
② 画面的三维：走进院子能看见房子、桌子、人——这个 App 现在没有
```

**建议顺序**：先把 P0–P2 做完，让世界在数据上真活；再做「一个房间的 3D 场景」作为展示层（Flutter 端接 3D 渲染，或直接做一个 WebGL 场景嵌进来）。  
否则会做成「漂亮的空房子」——人进去没事可做，比现在还假。
