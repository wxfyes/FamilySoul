# 降本清单 —— 主号对话成本优化

> 问题：**相公账号单轮成本是成员号的 6 倍，且缓存命中率 0。**
> 目标：保持上帝视角，把单轮成本压到现在的 1/3 ~ 1/5。

---

## 一、现状数据（线上实测）

| 账号 | 提示字数 | 输入 tokens | 缓存命中 |
|---|---|---|---|
| 紫嫣（成员号） | 1,539 字 | 1,544 | 0 |
| **相公（主号）** | **12,617 字** | **9,262** | **0** |

**单轮成本 ≈ 6 倍。长期聊，主号就是烧钱的那个。**

---

## 二、五条根因

```
① 主号走"上帝视角"分支：天机全量 + 内宅规则 + 关系网 + NPC 主线 + 旧事 + 历史
② 缓存命中 0：动态内容（时间/天机）排在前面 → 每轮前缀都变 → 永远不命中
③ 重复规则：内宅规则、婉儿优先、严禁下厨房等大段，每轮重复
④ 历史窗口 8 轮（historyTurns=8），且每条都可能很长
⑤ 额外调用：记账员 + 代演（最多 3 次），每次都是完整请求
```

---

## 三、措施（按省钱效率排序）

### ① 缓存友好化：固定块在前，动态块在后 ⭐ 最值钱

**现状**：系统提示里混着动态内容（时辰、天机），每轮都变。

**改法**：

```
[系统提示 前段] 人设 + 规则 + 输出格式   ← 一字不变，可缓存
[系统提示 后段] 天机 / 在场 / 旧事        ← 每轮变
[用户消息]      历史 + 这句话
```

**关键**：DeepSeek 的上下文缓存只认**前缀**。只要前 2~4k tokens 稳定，就能命中。

**预期**：缓存命中 50~70%，输入费降到 **1/3 甚至 1/10**（DeepSeek 缓存价差极大）。

**验收**：`[Cost] 输入 X（缓存命中 Y / 未命中 Z）` 里 Y > 0 且逐轮上升。

---

### ② 删重复规则段

**位置**：`src/pet-service.js` 里几段写死的内宅规则：

```
"只要婉儿在场……【正妻·婉儿】必须率先发话主持大局！"
"妾室芸娘与丫鬟小翠只能顺着主母的话从旁帮衬，严禁反客为主！"
"严禁主母下厨房炖汤死板套路……"
```

**这些既是剧本，又每轮重复上千字。**

**预期**：-15% ~ -20%，**顺便去剧本化**。

---

### ③ 天机按需裁剪

**现状**：全城 150+ 人、全部主线、旧事全带上。

**改法**：

```
只带：在场者 + 直接相关的人（≤ 8 人）
只带：本轮话题命中的关系/事件（≤ 3 条）
不带：全城名册、无关主线、全部旧事
```

**预期**：-30%。

---

### ④ 历史窗口收窄 + 摘要化

**现状**：`historyTurns = 8`，每条可能几百字。

**改法**：

```
最近 4 轮原文 + 更早的压成一句"前情提要"
```

**预期**：-10%。

---

### ⑤ 输出长度与温度

```
maxTokens: 160 → 100~120
```

**输出费直接砍 1/3**。

---

### ⑥ 记账员与代演按需

**现状**：每轮可能额外 1~3 次完整调用。

**改法**：

```
闲聊/无状态变化 → 不调记账员
只有点名/需要应声时才代演，最多 1 次
```

**预期**：省掉 1~2 次完整请求，**这部分省的是真金白银**。

---

### ⑦ 模型分层（可选）

```
主模型：deepseek-chat（剧情与决定）
记账员：更小更便宜的模型
代演：可用便宜模型
```

**前提**：便宜模型要能守住格式（千问那种不行）。

---

## 四、预期总账

| 措施 | 输入节省 | 备注 |
|---|---|---|
| ① 缓存友好化 | **-50% ~ -90%**（命中部分） | 最值钱 |
| ② 删重复规则 | -15% ~ -20% | 顺带去剧本 |
| ③ 天机裁剪 | -30% | 只带相关 |
| ④ 历史收窄 | -10% | 4 轮 + 摘要 |
| ⑤ 输出限长 | — | 输出费 -33% |
| ⑥ 减少额外调用 | — | 每轮省 1~2 次请求 |

**叠加后：单轮 ≈ 现在的 1/3 ~ 1/5。**

---

## 五、`解耦后会不会好`

**会好，但方向要对。**

```
❌ 错解：把主号绑成 actor，走成员分支
   → 便宜了（1.5k），但天机、关系网、NPC 主线全丢了
   → 你从"上帝"变成"路人"，世界不动了

✅ 正解：保持上帝视角，但把"固定/动态"分开
   → 缓存命中，成本降，视野不降
```

---

## 六、验收指标

```
① [Cost] 缓存命中 > 0，且逐轮提高
② 单轮提示字数：12,617 → 6,000 以下
③ 单轮输入 tokens：9,262 → 5,000 以下
④ 每轮额外调用：≤ 1 次
⑤ 对话质量不降：多人同场、认人、不失忆（跑 14 条回归）
```

**第 ⑤ 条最重要——省钱的代价不能是变傻。**

---

## 七、一条提醒

```
省钱不能靠"删掉世界"。
只能靠"同一份世界，说法更省"。
```

**天机可以裁剪，但不能裁到 NPC 不认识人、不记得事。**

# 附：数据会长多大，怎么自动备份

## 一、先说结论

```
真正会撑爆的不是 state.json（一年也就几百 KB）
是 ① 语音 wav 文件  ② 聊天历史
```

**state 是"账本"，很轻；音频和对话是"录音带"，很重。**

## 二、实测与估算

### 现在（第 15 日，150+ 人物）

| 文件 | 大小 | 说明 |
|---|---|---|
| `state.json` | ~95 KB（本地实测） | 150 人、关系网、产业、案子 |
| `history-*.json` | 4~35 KB / 人 | 每轮约 0.3~0.5 KB |
| `*.wav` | 20~60 KB / 条 | 每条语音一个文件 |
| `milestones.json` | 2 KB | 大事记 |

### 一年后会怎样

| 项目 | 增长估算 | 一年后 | 处理 |
|---|---|---|---|
| `state.json` | +5~10 KB/日 | **300~600 KB** | 不用管 |
| `events.jsonl` | 30 条/日 × 300 B | **3 MB** | 按月切分压缩 |
| 聊天历史（4 人） | 100 轮/日 × 0.5 KB | **~70 MB** | 按月归档 + gzip（压到 ~7 MB） |
| **语音 wav** | 100 条/日 × 40 KB | **~1.4 GB** | **保留 7 天，其余删或转码** |
| 每日快照 | 300 KB × 23 份 | **~7 MB** | 三级保留 |

**结论：一年总量可控在 50 MB 以内——前提是音频有保留策略。**

## 三、四个"自家能解决"的办法

### ① 音频：保留 7 天，超期删

```
data/audio/*.wav  → 只留最近 7 天
更早的：删掉（需要时重新合成）
或转 mp3（体积压到 1/10）
```

**这一条就能把 1.4 GB 压到 30 MB 左右。**

### ② 聊天历史：按月切分 + 压缩

```
history-husband.json → history-husband-2026-11.json.gz
保留最近 3 个月原文，更早的压成摘要（每 50 轮一条）
```

### ③ 快照：三级保留

```
每日 1 份，保留 7 天
每周 1 份，保留 4 周
每月 1 份，保留 12 月
超出自动删最旧的
```

### ④ state 自己瘦身

```
appliedActions：只留最近 500 条（已有 prune）
memories：上限 500 条，超了按时间淘汰
bonds：只留 |score| ≥ 15（已有）
events：只留最近 30 天进 state，其余进 jsonl
```

## 四、自动备份（不需要人管）

### 方案：每日一次，本地 + 异地

```
每天 03:00
  ① 打包：state.json + events + 历史 + 快照索引 → backup-YYYYMMDD.tar.gz
  ② 存本地：/opt/familysoul/backups/（保留 14 天）
  ③ 推到异地：192.168.1.112（开发机）或你的网盘
  ④ 每周日：把最新一份再存一份到"周备份"（保留 8 周）
```

**用 systemd timer 或 crontab 都行，一条命令的事。**

### 恢复演练（每季度一次）

```
拿一份周备份 → 在临时目录解包 → 起服务 → 确认世界能读
```

**没演练过的备份，等于没有备份。**

### 体积控制

```
tar.gz 压缩后，state+events+history 约 1~5 MB/天
14 天 ≈ 20~70 MB
加周备份 8 份 ≈ 再加 40 MB
总占用 < 150 MB
```

## 五、一句话

```
数据不是"会爆炸"，是"没人管就会慢慢堆"。
设好保留期，它自己就稳了。
```

**三件事必须做：音频 7 天、历史按月压、快照三级留。**

## 六、验收

```
① 跑 30 天后，data/ 总量 < 100 MB
② 随机抽一份 7 天前的备份，能恢复
③ 删音频后，旧对话仍能正常显示文字
④ 快照只留规定份数，不会无限涨
```

# 附二：备份脚本用法（`scripts/backup.mjs`）

## 一、它绝对安全

```
① 只读 data/，绝不写 data/
② 不删任何东西，除非你加 --prune
③ 默认 dry-run：先告诉你"会删什么"，不真删
④ 备份失败不影响正在跑的服务
```

**它只做两件事：把 data 压成 .gz 放进 backups/；按保留策略清理 backups/ 里的旧份。**

## 二、四条命令

```bash
# ① 只备份（最常用，可挂定时任务）
node scripts/backup.mjs

# ② 备份 + 清理过期备份
node scripts/backup.mjs --prune

# ③ 备份 + 清理备份 + 删除 7 天前的语音
node scripts/backup.mjs --prune --prune-audio 7

# ④ 校验最近一份备份是否完好
node scripts/backup.mjs --verify
```

**输出示例：**

```
✓ 备份完成：6 个文件 → backups/2026-11-03
  原始 136.2 KB → 压缩 25.2 KB
  · world/state.json  95.4 KB
· 没有过期备份需要清理
  日备份保留 14 天，周备份保留 8 份
```

## 三、保留策略

```
日备份：保留 14 天
周备份：每周日那份自动留 8 份（不受 14 天限制）
语音：--prune-audio 7 → 只留 7 天
```

**周备份是"防连续误删"的保险**：日备份全被覆盖，还能回到上周。

## 四、挂定时任务

### 软路由（cron）

```bash
# 每天 03:10 备份 + 清理
10 3 * * * cd /opt/familysoul && /usr/bin/node scripts/backup.mjs --prune --prune-audio 7 >> backups/backup.log 2>&1
```

### 或 systemd timer

```ini
# /etc/systemd/system/familysoul-backup.service
[Unit]
Description=FamilySoul backup

[Service]
Type=oneshot
WorkingDirectory=/opt/familysoul
ExecStart=/usr/bin/node scripts/backup.mjs --prune --prune-audio 7
```

```ini
# /etc/systemd/system/familysoul-backup.timer
[Unit]
Description=Daily FamilySoul backup

[Timer]
OnCalendar=*-*-* 03:10:00
Persistent=true

[Install]
WantedBy=timers.target
```

```bash
systemctl enable --now familysoul-backup.timer
```

## 五、异地一份（可选，但建议）

```bash
# 每天把当日备份推去开发机
scp -r /opt/familysoul/backups/$(date +%F) root@192.168.1.112:/backup/familysoul/
```

**同一块硬盘上的备份，挡不住硬盘坏。**

## 六、恢复怎么做

```bash
# ① 停服务
cd /opt/familysoul && ./stop.sh

# ② 解压当天备份（覆盖前先自己留一份）
cp -r data data.bak-$(date +%s)
gzip -d -c backups/2026-11-03/world/state.json.gz > data/world/state.json
gzip -d -c backups/2026-11-03/world/milestones.json.gz > data/world/milestones.json

# ③ 起服务
./start.sh
```

**恢复后第一件事：跑 `node scripts/backup.mjs --verify`，确认新备份也能生成。**

## 七、三条纪律

```
① 恢复前一定先备份现状（data.bak-时间戳）
② 每月至少做一次 --verify
③ 每季度真恢复一次到临时目录试跑，别等出事才第一次用
```

**没演练过的备份，等于没有备份。**
